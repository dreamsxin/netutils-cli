# 批量与可观测性 — 需求

**Spec**: `batch-and-observability`
**里程碑**: v0.7.0
**状态**: 已评审（requirements）→ 进入 design

## 1. 背景

工具目前能把单个目标诊断得很细，但无法把结果用于巡检与监控。三个缺口实际上是同一个能力的三面：

- **只能接单目标**。每个目标参数都是单个位置 `String`（`src/cli.rs:184` scan、`:196` check），全仓没有任何 `io::stdin()` 调用，也没有 `--file` / `@file`。巡检 200 个端点必须靠外层 shell 循环，而每份输出里除单个 `target` 字段外没有可关联标识，结果拼不回一张表。
- **探测记录没有时间戳**。`ProbeResult`（`src/ping/mod.rs:13-19`）与 `CheckProbe`（`src/connectivity/mod.rs:24-32`）只有 `seq` / `rtt_ms`。输出无法与其他遥测对齐时间线，无法事后画趋势，也无法作为带日期的工单证据。全项目唯一的时间戳是 `diag` 的一个墙钟字符串（`src/diag/mod.rs:399-415`）。
- **输出出不去**。`OutputMode` 只有 `Table` / `Json`（`src/output.rs:10-15`），一切走 `println!`，JSON 是 `to_string_pretty` 的多行大对象且在全部探测结束后才输出（如 `src/connectivity/mod.rs:146-149`）。长跑探测无法边跑边入库。唯一的行分隔输出是 `ping --count 0`（`src/ping/mod.rs:119-123`），且 `print_json_line` 是 `ping` 模块私有函数（`src/ping/mod.rs:172`）。

## 2. 目标

让 `check` 与 `scan` 可以用于**批量巡检**，并让所有探测输出**可被机器按时间关联与流式消费**。

## 3. 非目标

- 不做 CIDR 展开（`scan 192.168.1.0/24`）。留待后续 spec。
- 不做 CSV / Prometheus / statsd 输出。本 spec 只做 NDJSON。
- 不做配置文件与 profile。
- 不做写文件（`--output`）。NDJSON 加 shell 重定向已足够，保持 `src/output.rs` 不引入 writer 抽象这一现状。
- 不给 `ping` / `http` / `tls` 等其他命令加批量输入。先在 `check` / `scan` 验证契约。
- `--assert` 的 p50/p95/p99 空洞属独立 spec，不在本 spec 范围内。

## 4. 用户故事

- **US1** 作为运维工程师，我有一份 200 行的端点清单，我希望一条命令跑完并得到一份可解析的汇总，而不是写 shell 循环再手工拼结果。
- **US2** 作为运维工程师，我在排查间歇性故障，我希望每条探测记录都带时间戳，这样能和交换机日志、应用日志对齐到同一分钟。
- **US3** 作为平台工程师，我希望把长跑探测的输出直接管进日志采集，每行一条 JSON，而不是等命令结束才拿到一坨。
- **US4** 作为现有脚本的维护者，我希望升级后我那些只测单目标的脚本不用改。

## 5. 需求

### R1 多目标输入

`check` 与 `scan` 应支持从文件或标准输入读取目标清单。

**验收标准**

- `netutils check --targets-from targets.txt` 依次探测文件中每个目标。
- `--targets-from -` 从标准输入读取。
- 位置参数 `target` / `host` 与 `--targets-from` 互斥；两者都给出时以退出码 2 报 CLI 用法错误，且不发出任何探测。
- 两者都不给出时同样以退出码 2 报错。
- `scan` 的 `ports` 位置参数在批量模式下仍生效，对清单中每个主机使用同一份端口集合。

### R2 目标清单格式

清单格式应足够宽容，便于人手维护。

**验收标准**

- 每行一个目标；行首尾空白被裁剪。
- 空行被忽略。
- `#` 起始的行被忽略（整行注释）。行内 `#` **不**视为注释，因为目标字符串中可能出现该字符。
- 保持文件中的顺序，不去重（重复目标是合法的，用户可能有意重复采样）。
- 文件不存在、无读权限、或内容为空（去掉注释与空行后无有效目标）时，以退出码 2 报错并不发出任何探测。
- 单个目标的格式错误（如 `check` 的目标缺端口）不应中断整批：该目标记为失败并带错误原因，继续处理后续目标。

### R3 批量执行的并发与输出顺序

批量执行应可控并发，且输出顺序确定。

**验收标准**

- 有一个参数可控制**同时探测的目标数**，默认 1（串行），与 `check` 已有的 `--concurrency`（同一目标内的探测并发）语义不冲突、命名不混淆。
- 无论实际完成顺序如何，`--json` 的汇总结果按清单原始顺序排列。
- NDJSON 模式下每行在对应目标完成时即输出，顺序可与清单不同；每行必须带目标标识与序号，使消费方能重排。

### R4 探测记录时间戳

每条探测记录应带发起时刻。

**验收标准**

- `check` 的每条探测记录、`scan` 的每个端口结果、`ping` 的每条探测记录都新增时间戳字段。
- 时间戳为 UTC、RFC 3339 格式、毫秒精度，如 `2026-09-23T07:54:29.412Z`。
- 时间戳记录的是该次探测**发起**的时刻，而非结果写出的时刻。
- 表格模式默认不显示时间戳（避免刷屏），由一个开关开启。

### R5 运行级时间戳

每次运行应可判断其覆盖的时间窗口。

**验收标准**

- 运行级输出新增开始与结束时刻两个字段，格式同 R4。
- 批量模式下每个目标的子结果各自带有自己的开始与结束时刻。

### R6 NDJSON 流式输出

应支持行分隔 JSON，一条记录一行，即时输出。

**验收标准**

- 新增一个全局开关开启 NDJSON；该开关隐含 JSON 输出，无需同时传 `--json`。
- 每行是一个**紧凑**（非 pretty）JSON 对象，以 `\n` 结尾，且每行自带足以独立解读的上下文（目标、时刻、记录类型）。
- 每行输出后立刻可被下游读取，不等整批结束。
- 每条记录带类型标识，使消费方能区分「单次探测」与「汇总」。
- 同时传 `--json` 与 NDJSON 开关时以 NDJSON 生效，不报错。

### R7 单目标向后兼容

现有脚本不应因本次改动而失效。

**验收标准**

- 未使用 `--targets-from` 且未使用 NDJSON 开关时，`check` / `scan` / `ping` 的 `--json` 顶层结构与 0.6.0 保持一致：不改字段名、不改字段类型、不改嵌套层级。
- 仅允许**新增**字段（R4 / R5 的时间戳）。
- `ping --count 0 --json` 现有的「逐行探测 + 末尾汇总」行为保持不变。

### R8 批量退出码

批量运行的退出码应反映最坏结果。

**验收标准**

- 全部目标成功 → 0。
- 任一目标探测失败 → 1。
- 清单或参数层面的用法错误 → 2，且不发出探测。
- 任一目标的 `--assert` 断言失败 → 3（沿用 `src/assertion.rs:20` 的既有约定）。
- `--total-timeout` 超时 → 124，覆盖上述任何码。
- 单个目标失败不终止整批。

### R9 表格模式的批量呈现与实时进度

表格模式下批量结果应可读，且**必须边跑边出**。

**验收标准**

- 每个目标有可见的分段标识或带目标名的结果行。
- **任何情况下都不允许把输出缓冲到整批结束再打印。** 排障是本工具的唯一用途，缓冲会让「卡在哪一步」无法判断。
- `--parallel == 1` 时保持逐次探测的实时输出不变。
- `--parallel > 1` 时抑制单目标内部的逐次行（并发下必然交错到不可读），改为每个目标完成即打印一行带完成计数器与目标名的结果。
- 全部目标结束后给出一行总览：目标总数、成功数、失败数。

### R9b 中断可见性

被中断或卡住时，已经发生的事情必须已经打印出来。

**验收标准**

- 在任意时刻按 Ctrl-C，此前已完成的目标结果都应已经出现在输出里，而不是随进程退出一起丢失。


### R10 时间戳实现不引入新依赖

**验收标准**

- 不新增 `chrono`、`time` 或任何日期库。`src/diag/mod.rs:399-415` 的 `current_timestamp` 已明确注明「简单时间戳，不依赖 chrono」，本 spec 沿用该决定，改为提升并扩展该实现。
- 该实现有单元测试覆盖已知日期（闰年、月末、跨年）。

### R11 中断处理

批量运行被中断时不应丢失已采集的数据。

**验收标准**

- 批量模式下 Ctrl-C 停止发起新探测，输出已完成目标的结果与总览，退出码非 0。
- 沿用 `ping` 已有的 `sleep_or_interrupt` 范式（`src/ping/mod.rs:159-169`），不再另造一套信号处理。

### R12 文档与 i18n

**验收标准**

- `README.md` 新增批量巡检与 NDJSON 消费的示例。
- 所有新增用户可见字符串走 `t()` / `t2()`，`zh` 与 `en` 均补齐（`src/i18n.rs`）。
- 新增的全局开关同步登记到三处：`Cli`、`PluginCli`、`GLOBAL_FLAGS`（`src/main.rs:384-389`）。
- `CHANGELOG.md` 建档并记录本次新增字段。

## 6. 兼容性影响

本 spec 只新增字段，不改既有字段，因此**不构成破坏性变更**。真正的破坏性变更在 v0.8.0 的端口三态（`scan` 的 `open: bool` → `state: string`）。这也是把批量与可观测性排在三态之前的原因：先把输出契约的扩展方式立好，再动既有字段。

## 7. 未决问题

三个问题已在 `design.md` 第 0 节定稿，此处只留结论：

- **Q1** 目标并发参数命名 → `--parallel <N>`，与既有 `--concurrency`（目标内部并发）正交。
- **Q2** NDJSON 记录类型字段 → `record`，取值 `probe` / `summary` / `batch_summary` / `error`。
- **Q3** 批量模式下 `--assert` 语义 → 逐目标独立断言；任一失败即退出码 3。
